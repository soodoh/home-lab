# Proxmox Ansible-to-Nix ownership migration matrix

## Purpose and fixed boundaries

This matrix is the reviewed ownership ledger for replacing only the Proxmox host path with a Nix-built reconciler. It does not authorize implementation or live mutation by itself.

The migration preserves these boundaries:

- Proxmox VE remains the official Debian-based appliance. The host is not converted to NixOS and does not use `proxmox-nixos`.
- [`../infrastructure/contract/home-lab.yml`](../infrastructure/contract/home-lab.yml) remains the single authoritative desired-state contract. Nix consumes a validated deterministic projection; it does not copy contract values into a second model.
- OpenTofu continues to own VM 100, its recovery image, and PVE PCI/USB mapping resources. The Nix host reconciler may validate those objects but must not create, update, delete, import, or rewrite them.
- Ansible remains the owner of Arch guest configuration, Compose deployment, and application recovery. OpenTofu, not Ansible, owns VM 100. Shared Ansible roles remain while the guest and application paths use them.
- PVE cluster state under `/etc/pve` is reconciled only through supported `pveum`, `pvesh`, `pvesm`, or PVE API operations, never through generic file replacement or Nix-store symlinks.
- Nix runs only on the trusted controller. No Nix daemon, store, or package installation is added to the PVE host; the host receives ordinary root-owned versioned observer and activator helpers.
- Protected credentials and hardware identities are runtime inputs. They do not enter Git, Nix derivations, Nix store paths, Nix host plans, logs, fixtures, or committed evidence. Plans expose only redacted counts/booleans; protected keyed attestations, when required for preconditions, remain outside shareable evidence. Plaintext and stable unkeyed hashes of protected identifiers are prohibited.
- Completed migrations are archived as evidence and recovery notes. They are not reintroduced into steady state.
- Routine PVE UI use is read-only. Reviewed Git configuration, pinned Nix inputs, versioned upstream package expectations, protected identities, and backups are the reconstruction inputs.

## Current composition and target entry points

The current local bootstrap is `ansible/playbooks/proxmox-bootstrap.yml`; the current steady path is `ansible/playbooks/proxmox-site.yml`. Both load the contract and `ansible/group_vars/proxmox_hosts.yml`, acquire `apply_lock`, and compose the Proxmox-specific and shared roles. The bootstrap additionally requires local execution, physical-console/trusted-LAN gates, and an official PVE installation. The steady play adds firewall, health, and cleanup.

The target interface is:

```sh
nix run .#proxmox-host -- plan
nix run .#proxmox-host -- apply --plan <reviewed-plan>
nix run .#proxmox-host -- verify

nix run .#proxmox-bootstrap -- plan
nix run .#proxmox-bootstrap -- apply --plan <reviewed-plan>
nix run .#proxmox-bootstrap -- verify
```

These commands execute on the trusted controller. Fresh-PVE bootstrap uses console-backed trusted-LAN root transport to install the exact bundle's fixed observer/activator as ordinary root-owned files; it never uploads arbitrary code for privileged execution and never installs Nix on PVE. Bootstrap must end with `verify` and an empty bootstrap plan before controller capabilities are transferred or OpenTofu proceeds.

The Nix host `plan` is non-mutating and secret-free. It binds the Git commit and tree, validated contract projection, `flake.lock`, the bundle's canonical content SHA-256 (independent of its input-addressed Nix store path), normalized redacted observed-before-state digest, typed action preconditions and freshness limit, and plan hash. `apply` acquires both locks, re-observes every affected precondition, and fails on stale or changed state without deriving replacement actions or implicitly replanning. `verify` performs live health and drift checks and must be followed by an empty plan. Retained OpenTofu binary saved plans remain protected mode-0600 local artifacts and may encode sensitive provider inputs under their existing manifest, policy, and credential safeguards; the Nix host plan/evidence exclusion does not redefine that retained boundary.

All mutable domains share one root-owned non-store rollback area whose manifest is bound to the reviewed plan. It requires strict modes, symlink refusal, free-space/capacity checks, bounded retention, and explicit handling for sensitive access captures; successful cold-boot qualification either securely removes each capture or records an approved bounded preservation decision. Network, SSH, firewall, and Tailscale actions additionally prearm host-local timed rollback watchdogs before mutation and cancel them only after local and independent controller canaries pass.

## Package and reproducibility policy

The Nix flake pins the controller toolchain and renderer through `flake.lock`; it does **not** preserve external Debian, Proxmox, kernel, ZFS, firmware, or Tailscale packages. The authoritative contract declares selected exact versions, semantic critical-package roles, prohibited packages, architecture, and the path and SHA-256 of the canonical expected installed manifest. The hash-bound manifest is a generated expected-state and solver-closure artifact, not an independently edited second desired-state list. Its timestamp-free, host-identity-free provenance binds the SHA-256 and installed-record count of a `dpkg` status TSV to the SHA-256 and normalized transitions of the reviewed joint APT simulation. Contract projection and bundle generation must therefore record:

1. repository file paths, types, URIs, suites, components, and signing-key paths;
2. approved signing-key download checksums where the key is not supplied by a pinned Debian/PVE package;
3. exact versions for every directly selected host package, including the reviewed PVE kernel/header and relevant ZFS/PVE package set;
4. the normalized full expected installed-package manifest used as the audited solver-result/dependency-closure gate; and
5. the expected native service set.

Planning refreshes authenticated metadata in an isolated APT state, reports exact unavailable `name=version` diagnostics, and runs one `apt-get --simulate --no-remove --no-install-recommends --no-allow-downgrades` transaction for all selected versions. It applies every recognized simulated transition to the complete installed `dpkg` map and requires byte-for-byte package-name/version parity with the canonical manifest; a malformed transition, unexpected install, removal, version change, or foreign architecture fails planning. During an approved non-check run, that same helper installs the exact package specifications with the same isolated authenticated lists, keyrings, and cache, with real dpkg locking, no removal, recommends, or downgrade, and then re-observes the complete installed map. There is no separate live-cache refresh or Ansible APT mutation path.

A package-policy update starts with a fresh status-bearing inventory such as `${db:Status-Abbrev}\t${binary:Package}\t${Version}` and a saved joint `apt-get --simulate` result for the reviewed exact selection. Regenerate with `scripts/render-proxmox-package-manifest --inventory <status.tsv> --simulation <apt-simulation.log> --architecture amd64 --output infrastructure/contract/proxmox-package-manifest.json`, review every normalized transition and the final complete set, update selected versions and the manifest SHA-256 in the contract, and run the contract/package tests. Every status whose second Status-Abbrev character is `i` is installed inventory (including held or reinstreq selections); states such as `rc` are excluded. Neither the manifest nor its provenance includes timestamps or host identity. The renderer accepts only observed inventory plus simulation inputs; do not hand-edit the manifest or update its hash without regenerating and reviewing both inputs.

The project deliberately adds no APT mirror, snapshot service, private package cache, or retained `.deb` recovery cache. A future upstream garbage-collection event may require a normal reviewed contract/package-version update before recovery; that residual dependency is accepted and must be reported, never hidden behind a mutable “latest” install.

## Live and cold-boot qualification gate

Before cutover, capture an Ansible no-op baseline and a Nix audit plan at the same committed revision and live state. The cutover apply requires explicit operator approval, physical console, tested trusted-LAN rollback, current backups, healthy ZFS, VM 100 protection/state confirmation, no other mutation, and exact commit/tree, `flake.lock`, contract/projection, canonical bundle-content, redacted observed-state, and plan hashes. After both locks are acquired, every affected precondition is re-observed within the plan freshness limit; any mismatch stops without replanning.

After apply and again after a cold boot, verify at minimum:

- management bridge/address, gateway/DNS, LAN rollback, Tailscale, both SSH service identities, and human access;
- PVE UI and authenticated API, roles, ACLs, and token rotation/transfer state;
- exact repositories, signing-key hashes, package versions, running/retained kernel, initramfs, GRUB/proxmox-boot-tool, and native services;
- ZFS pool GUID/topology/health, datasets/mounts, PVE storage registration, NFS export, VM mount, and bounded read/write canary;
- PVE firewall state and permitted/denied paths;
- IOMMU/VFIO, Coral/GPU/audio bindings, host iGPU binding, USB mappings, and absence of prohibited legacy modules/rules;
- VM 100 startup, protection, OpenTofu no-op, workload/application health, and backup freshness;
- reconciler lock cleanup/failed-apply diagnostics; and
- `verify` success followed by a deterministic empty `plan` for the exact deployed commit and bundle.

Evidence is secret-free and schema-validated. It records the commit, contract hash, bundle hash, plan hash, host identity, before/after boot IDs, cold-boot fact, running kernel, domain outcomes, and timestamps. It does not record tokens, SSH keys, hardware serials/by-id paths, pool GUIDs, backup contents, or protected controller locations.

## Residual risks

- Exact Debian/PVE/Tailscale versions can disappear from upstream repositories; `flake.lock` cannot recover them.
- Debian/PVE activation is not a NixOS generation and has no atomic whole-host rollback. Each domain needs explicit pre-apply capture and native recovery.
- Network, SSH, Tailscale, and firewall changes can remove remote access despite local validation; console and trusted-LAN rollback remain mandatory.
- Kernel, initramfs, boot, ZFS, and VFIO changes may fail only after reboot; cold-boot qualification is therefore a release gate, not optional evidence.
- PVE token values are one-time secrets. Missing escrow requires rotation, not attempted reconstruction.
- ZFS/data state and VM 100 are validated across ownership boundaries; the Nix reconciler must fail closed rather than taking ownership when another owner is unhealthy.
- Upstream package, Tailscale control-plane, Git remote, and official PVE installer availability remain external recovery dependencies.
